# npm

Конфиг: .npmrc. Он задаёт адрес реестра, но не определяет поведение-lock-файла.

## Lock пинит resolved-URL

В lock-файле у каждой записи есть поле `resolved` с полным URL. `npm ci` берёт архив оттуда, а не из текущей настройки registry. Отсюда проверяемое утверждение: при существующем lock с публичным `resolved` подмена реестра в `.npmrc` не меняет источник скачивания.

Проверка:

```
grep -n '"resolved"' package-lock.json | head
npm config get registry
rm -rf node_modules && npm install --package-lock-only
grep -n '"resolved"' package-lock.json | head
```

Ожидаем: до пересборки в выводе публичный хост, после — {{NPM_REGISTRY_URL}}. Если после пересборки хост остался публичным, проблема не в `.npmrc`, а в том, что lock не был переписан (пункт 9).

## replace-registry-host

Я не буду утверждать наизусть список допустимых значений и умолчание для вашей версии npm. Проверьте сами:

```
npm --version
npm config get replace-registry-host
npm help config
npm config ls -l | grep replace-registry-host
```

Ожидаем: ключ присутствует, текущее значение видно в выводе. Смысл настройки — подменять хост в `resolved` при записи lock; файл .npmrc ставит её в `always`. Если на вашей версии ключ отсутствует, полагаться на него нельзя — тогда остаётся только пересборка lock-файлов (пункт 9).

## always-auth

`always-auth=true` заставляет npm посылать токен даже на чтение. Для приватного реестра это ожидаемое поведение; для публичного — лишняя утечка токена. Проверить: `npm config get always-auth`.

## ignore-scripts как trade-off

`ignore-scripts=true` запрещает lifecycle-скрипты, включая postinstall. Это ломает esbuild, sharp, node-gyp и любые пакеты, чья сборка опирается на установку бинарника. Это не бесплатная победа и не «надёжная защита»: часть пакетов перестаёт работать, а часть просто перестаёт получать обновления.

Проверка перед включением:

```
npm install --ignore-scripts
npm run build
```

Ожидаем: либо сборка проходит, либо список пакетов, которые нужно перевести на prefetch бинарников. Граница: даже разрешённый пакет с postinstall выполняет код после прохождения гейта — см. BOUNDARIES.md.

## git и tarball

Зависимости вида `git+https://...` и tarball-URL не проходят через реестр (пункт 17). Проверить в репозитории:

```
grep -R -n -E 'git\+|https?://.*\.tgz|github:' --include='package*.json' .
```

Ожидаем: совпадений нет либо каждый случай явно разобран. Сетевые хосты для таких зависимостей перечислены в ../egress-allowlist.md.
