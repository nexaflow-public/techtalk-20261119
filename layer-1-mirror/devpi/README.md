# devpi: зеркало против приватного индекса

Разница та же, что между двумя конфигами Verdaccio. Зеркальный индекс — это индекс, у которого в `bases` стоит публичный `root/pypi`: неизвестный пакет уходит на PyPI и резолвится. Приватный индекс с явным наполнением — это индекс без публичного base, куда пакеты попадают только по явной загрузке. Запрет неразрешённого получается не отдельной настройкой «deny all», а отсутствием публичного base.

Я не уверен в точной семантике `bases` и в том, как devpi ведёт себя при запросе неизвестного пакета в вашей версии, поэтому готовый конфиг здесь не привожу. Что нужно проверить и как.

## (а) Что именно проверить

1. Есть ли у целевого индекса публичный base `root/pypi`.
2. Что возвращается на запрос неизвестного пакета: 404 или проксированный ответ с PyPI.
3. Требуется ли аутентификация на запись (`acl_upload`) и может ли разработчик создать свой индекс.
4. Отдаётся ли отозванный/upstream-удалённый пакет из кеша после удаления (пункт 25).

## (б) Команды проверки

```
devpi use http://localhost:3141/<user>/<index>
devpi index -l
devpi index <user>/<index> bases=
devpi install <имя-пакета-из-каталога>
curl -I http://localhost:3141/<user>/<index>/+simple/<неизвестный-пакет>/
```

## (в) Ожидаемый результат

- `bases` для приватного индекса пуст; публичный `root/pypi` в списке отсутствует.
- Пакет из каталога ставится; неизвестный пакет отдаёт 404 и не уходит на PyPI.
- Загрузка (`devpi upload`) требует аутентификации.
- После удаления пакета из storage повторный запрос перестаёт быть положительным.

## (г) Документация

- https://doc.devpi.net/latest/ — раздел про indices и `bases`;
- https://doc.devpi.net/latest/ — раздел про `devpi index` и ACL.

Если эта проверка покажет другое поведение, написанное выше нужно переписать под вашу версию; в репозиторий сознательно не положен неопробованный конфиг.
